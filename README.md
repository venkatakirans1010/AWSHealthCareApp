# Healthcare Claims AI

React + FastAPI healthcare claim intake with PostgreSQL persistence and private Amazon S3 PDF uploads. The existing dashboard, claim details, analytics, AI processing, evaluation, and settings routes are preserved; AI and enterprise workflows remain simulated.

## Run locally

Copy `.env.example` to `.env`, set `DATABASE_URL`, `POSTGRES_PASSWORD`, and the existing private `S3_BUCKET_NAME`, then authenticate through the standard AWS credential chain. Do not store AWS access keys in the project.

```powershell
.\venv\Scripts\python.exe -m pip install -r requirements.txt
docker compose up -d postgres
.\venv\Scripts\python.exe scripts\init_db.py
.\venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

In another terminal:

```powershell
npm install
npm run dev
```

Frontend: `http://localhost:5173`  
Swagger: `http://localhost:8000/docs`

## Claim API

- `POST /claims` creates a `RECEIVED` claim.
- `GET /claims?status=RECEIVED&limit=20&offset=0` lists claims.
- `GET /claims/{claim_id}` gets one claim.
- `POST /claims/upload` accepts a PDF as multipart form data, stores it at `incoming/{claim_id}/{filename}`, and creates the linked `RECEIVED` record.

IDs are generated by PostgreSQL's atomic `claim_number_seq`, beginning at `CLM10001`. Sequence values are concurrency-safe and are intentionally not reused after a rollback.

## Persistence and transaction boundaries

PostgreSQL is the source of truth for claim metadata and status; S3 is the source of truth for private document bytes. `claim_documents` stores the bucket and object key, never a public URL. Claim, document, and audit writes commit in one database transaction. Database failures roll back those writes. An S3 upload cannot participate in that transaction: if S3 fails, the database transaction rolls back; if S3 succeeds but the database commit fails, the API logs the orphaned object for an explicit retry or cleanup and does not report success. It does not automatically delete existing objects.

All timestamps are timezone-aware. Credentials stay in `.env` or the normal AWS credential chain and are excluded from source control. Future background processing should use retries and explicit processing states; extraction and decision tables are present but no AI processing is implemented here.

For Amazon RDS for PostgreSQL, use the same `DATABASE_URL` format with the RDS endpoint, keep the instance private where possible, restrict its security group to the application, require TLS, and use short-lived/IAM authentication or a managed secret for production.

Initial lifecycle:

```text
RECEIVED
  -> PROCESSING
  -> APPROVED / DENIED / REQUEST_INFORMATION / FRAUD_REVIEW
```

Only `RECEIVED` is assigned automatically in this milestone.

## Day 7: local Tesseract OCR

OCR runs locally with Tesseract; Amazon Textract is not used and no Textract IAM permissions are required. The workflow downloads an existing PDF from the configured private S3 bucket, renders every page at `OCR_RENDER_DPI` (200-300), captures Tesseract text plus word confidence/bounds, writes raw JSON under `output/ocr/`, and can upload it to `results/{claim_id}/tesseract_raw.json`. S3 request and storage charges still apply to those reads and optional writes, but there is no managed OCR per-page charge.

On Windows, install the current Tesseract distribution, ensure its `tesseract.exe` is on `PATH`, and verify it in a new terminal:

```powershell
tesseract --version
```

If it is not on `PATH`, set the executable explicitly in the git-ignored `.env` file (the typical path is shown in `.env.example`):

```dotenv
TESSERACT_CMD=C:\Program Files\Tesseract-OCR\tesseract.exe
TESSERACT_LANGUAGE=eng
OCR_RENDER_DPI=250
OCR_AUTO_VALIDATION_CONFIDENCE=95
OCR_VERIFICATION_CONFIDENCE=80
```

Install the Python wrappers with the normal project dependencies, then run a document already in S3:

```powershell
.\venv\Scripts\python.exe -m pip install -r requirements.txt
.\venv\Scripts\python.exe -m scripts.run_tesseract --claim-id CLM10001 --s3-key incoming/CLM10001/claim_10001.pdf
```

Add `--no-s3-result` to keep the result local. The field regexes live in `app/services/tesseract_service.py`; they are teaching rules for the current synthetic layouts and must be adapted for other layouts. The 95/80 confidence bands are configurable teaching thresholds, not official Tesseract recommendations. OCR confidence is not a correctness probability, field confidence is derived only from matching field evidence (never copied from the document average), and OCR quality/review flags do not approve or deny a claim.

`candidate_fields`, `field_review`, and the raw artifact location returned by the service are ready to be persisted through the existing `ClaimExtraction` model and `claim_extractions` table. This command intentionally does not write the database yet, so it can be tested independently and no duplicate repository or transaction path is introduced.

## Day 8: normalization and validation

Normalize the Day 7 raw artifact for an existing claim through the API:

```http
POST /claims/CLM10001/normalize
```

The service reads `results/CLM10001/tesseract_raw.json`, writes the independent normalized artifact to `results/CLM10001/normalized_extraction.json`, and upserts `claim_extractions` by `(claim_id, raw_ocr_artifact_key, raw_ocr_artifact_etag)`. A retry of the same raw object updates the same row. The normalized S3 upload occurs before the final database commit; if that commit fails, the API reports the uploaded artifact as a partial failure and leaves it available for reconciliation.

The default required fields are `patient_id`, `provider_id`, `diagnosis_code`, and `amount`. Override them only for the synthetic project schema:

```dotenv
NORMALIZATION_REQUIRED_FIELDS=patient_id,provider_id,diagnosis_code,amount
```

Normalization trims and collapses whitespace, preserves leading identifier zeroes, uppercases synthetic identifiers/codes, validates diagnosis and procedure syntax without claiming real-world code validity, parses money with `Decimal`, records currency only when a symbol/code is present, and rejects ambiguous numeric dates. Missing, malformed, or conflicting values generate stable structured flags. `COMPLETE` means configured validation passed; `REVIEW_REQUIRED` means normalization completed but needs human review; `FAILED` is reserved for an operational or unusable-OCR failure; `PENDING` is persisted while work is underway. These statuses never approve or deny a claim.

### Document Analysis Agent

`POST /claims/{claim_id}/analyze` runs the typed LangGraph workflow over documents already attached to the claim. Send `{}` to analyze every attached document, or provide an allow-listed subset:

```json
{
  "documents": [
    {"bucket": "configured-private-bucket", "key": "incoming/CLM10001/claim.pdf"}
  ]
}
```

An optional `X-Correlation-ID` request header is returned in the structured result; otherwise the API generates one. The workflow reuses the configured S3/Tesseract path and does not call an LLM. Existing `S3_BUCKET_NAME`, `TESSERACT_CMD`, `TESSERACT_LANGUAGE`, OCR confidence, and normalization settings apply.

### Policy Validation Agent

`POST /claims/{claim_id}/policy-validation` loads the claim's latest normalized extraction, preserves its persisted `INPATIENT` or `OUTPATIENT` claim type, retrieves raw policy chunks from Amazon Bedrock Knowledge Bases, applies deterministic payer/type/effective-date gates, and validates the bounded Bedrock model result. The optional request body records whether medical documentation is available:

```json
{"medical_documentation_available": true}
```

Configure `BEDROCK_KNOWLEDGE_BASE_ID`, `BEDROCK_POLICY_MODEL_ID`, and optionally `BEDROCK_POLICY_RETRIEVAL_RESULTS`. The service uses `AWS_REGION` and the standard boto3 credential chain; no credentials or resource IDs are embedded in code. Knowledge Base source metadata must provide `payer_id`, `claim_type` (or `service_type`), `effective_from`, `effective_to`, and preferably `policy_version`. Evidence without applicable metadata is excluded and routed for review. The endpoint reports policy coverage only; it does not approve or deny a claim.

### Medical Coding Agent

`POST /claims/{claim_id}/medical-coding` loads diagnosis and procedure candidates from the latest normalized extraction and validates them through the existing synthetic coding reference service. The optional body can supply documented descriptions, explicitly labeled clinical text, or evidence-derived confidence values:

```json
{
  "diagnosis_description": "Pneumonia, unspecified organism",
  "clinical_text": "Diagnosis Code: J18.9\nProcedure Code: 99223"
}
```

The LangGraph workflow uses deterministic reference lookups. It does not infer unlabeled codes or treat a reference match as proof of clinical coding correctness. The bundled JSON reference is illustrative training data, not a complete or authoritative ICD-10/CPT dataset. The coding API base URL remains configured through `CODING_API_BASE_URL`.

### Fraud Detection Agent

`POST /claims/{claim_id}/fraud-screening` loads the latest normalized extraction and retrieves comparison history through the existing authorized payer-history client. It performs anomaly screening only and never represents a confirmed fraud determination.

The documented additive scoring rules are capped at 100:

- possible exact duplicate: 50
- overlapping or unusually frequent service: 20
- billed amount greater than twice the applicable synthetic baseline: 25
- conflicting normalized fields: 20
- inconsistent synthetic service-type/procedure combination: 15

Scores at or above 30 require review. Any triggered rule is retained as an explainable review indicator even below that threshold. Missing required fields or unavailable history returns `INSUFFICIENT_DATA`, never `CLEAR`. Synthetic amount baselines are stored in `app/mock_services/data/fraud_baselines.json`; they are training fixtures, not production benchmarks.

### Claims Decision Agent

`POST /claims/{claim_id}/decision-recommendation` coordinates the trusted normalized extraction with the four typed specialist outputs. The graph initializes the correlation ID, validates claim/output identity, checks missing and conflicting facts, applies deterministic prerequisites, conditionally selects one of four recommendation routes, persists the recommendation, and produces the validated summary.

Routes are evaluated conservatively:

- missing documents, policy evidence, required codes, or authorization facts → `REQUEST_INFORMATION`
- specialist failure/timeout, identity conflict, coding ambiguity, unresolved policy conditions, or fraud indicators → `MANUAL_REVIEW`
- explicit applicable noncoverage with all other prerequisites resolved → `ELIGIBLE_FOR_DENIAL_REVIEW`
- all configured prerequisites resolved → `ELIGIBLE_FOR_APPROVAL_REVIEW`

Eligibility recommendations are stored in the existing `claim_decisions` table and leave the claim in `PROCESSING`; they never directly set `APPROVED` or `DENIED`. Information requests use `REQUEST_INFORMATION`. Manual routes use `FRAUD_REVIEW` only when fraud screening is unresolved, otherwise `PROCESSING`. No additional configuration or LLM call is required.

Illustrative COMPLETE output (values are synthetic, not hard-coded extraction results):

{

  "patient_id": "PAT1001",
  "patient_name": "Example Patient",
  "provider_id": "PROV1001",
  "payer_id": "PAY1001",
  "policy_id": "POL1001",

  "procedure_code": "99223",

## Day 9: Claim Details OCR workflow

Open a persisted claim and select **AI Processing**. That tab now provides the real examiner workflow:

1. Confirm the PDF name and private S3 object key under Document readiness.
2. Select **Run OCR** to call `POST /claims/{claim_id}/ocr` and display Tesseract metadata, candidate fields, field-specific confidence, validation outcomes, and raw artifact locations.
3. Select **Normalize Extraction** to call `POST /claims/{claim_id}/normalize` and display normalized fields, extraction status, review flags, and the normalized artifact key.
4. Refresh or reopen the claim. `GET /claims/{claim_id}/extraction` reloads the latest successfully persisted normalized extraction from PostgreSQL.

The UI never displays a public S3 URL and never changes the claim lifecycle status or makes an approval/denial decision. Raw OCR details are session-state only; rerun OCR after refreshing if candidate evidence needs to be inspected again. Normalized results persist across refreshes.

Run the application from the project root:

```powershell
.\venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
npm run dev -- --host 127.0.0.1
```

Validation commands:

```powershell
.\venv\Scripts\python.exe -m pytest -q
npm run typecheck
npm run build
```

Manual browser checklist:

- Open a claim whose response contains an `s3_object_key` and select AI Processing.
- Confirm Run OCR and Normalize Extraction are disabled for claims without an uploaded PDF.
- Run OCR and verify the candidate table contains response values rather than fixed demo data.
- Normalize and verify `COMPLETE`, `REVIEW_REQUIRED`, or `FAILED` appears independently of the claim badge.
- Refresh and verify the normalized extraction reloads.
- Recheck Claims, Upload Claim, Analytics, Evaluation, and Settings navigation.
